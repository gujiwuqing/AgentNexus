# 缺陷分级与优先级

> 用途：统一缺陷（Bug）的严重度、优先级定义与报告规范，让"这个 bug 有多严重、要不要现在修"有客观标准。
> 使用建议：挂载给「测试设计师」「代码评审员」Agent，用于评估缺陷等级、撰写规范的缺陷报告。

## 一、两个独立维度：严重度 vs 优先级

- **严重度（Severity）**：缺陷对系统/业务的**客观影响程度**。由测试/研发判定。
- **优先级（Priority）**：**修复的紧急程度与先后**。由产品/项目结合业务判定。
- 二者独立：可能"高严重度低优先级"（极端场景崩溃但几乎不触发），也可能"低严重度高优先级"（首页错别字，影响品牌需立即改）。

## 二、严重度定义

| 等级 | 名称 | 定义 | 示例 |
| --- | --- | --- | --- |
| S1 | 致命（Blocker） | 核心功能不可用/系统崩溃/数据丢失或错乱/资损/安全漏洞 | 无法下单、支付扣款不发货、越权看到他人数据 |
| S2 | 严重（Critical） | 主要功能受损，无合理绕过方案 | 优惠券计算错误、关键页面报错 |
| S3 | 一般（Major/Normal） | 功能缺陷但有绕过方案，影响有限 | 某筛选条件失效、偶发提示异常 |
| S4 | 轻微（Minor） | 体验/文案/样式问题，不影响功能 | 对齐错位、错别字、提示不友好 |

## 三、优先级定义

| 等级 | 含义 | 处理时限（参考） |
| --- | --- | --- |
| P0 | 立即修复，阻断发布 | 当天/小时级 |
| P1 | 本迭代内必须修复 | 迭代内 |
| P2 | 排期修复 | 后续迭代 |
| P3 | 可延后/择机 | Backlog |

## 四、严重度 × 优先级 参考矩阵

| | 高业务紧迫 | 中 | 低 |
| --- | --- | --- | --- |
| **S1 致命** | P0 | P0 | P1 |
| **S2 严重** | P0/P1 | P1 | P2 |
| **S3 一般** | P1 | P2 | P2/P3 |
| **S4 轻微** | P1（如涉品牌） | P3 | P3 |

## 五、缺陷报告规范（好的 Bug 单）

一个可被高效修复的缺陷报告应包含：

1. **标题**：`[模块] 简明现象`，一眼看懂。
2. **环境**：版本/分支、设备/浏览器、账号、环境（测试/预发/生产）。
3. **前置条件**：数据与状态。
4. **复现步骤**：编号、最小化、确定可复现。
5. **实际结果**：现象 + 错误信息/截图/录屏/日志/traceId。
6. **预期结果**：应该发生什么（引用需求/验收标准）。
7. **严重度/优先级**：初判，附理由。
8. **复现率**：必现 / 概率（如 3/10）/ 偶现。

**示例**：
```
标题：[支付] 使用满减券后实付金额比应付多 1 元
环境：v2.3.0，预发，账号 buyer01
前置：商品 99 元，满 50 减 10 券
步骤：
  1. 商品加购
  2. 结算页选择"满50减10"券
  3. 提交订单
实际：实付显示 90 元（应为 89 元），且下单成功
预期：实付 = 99 - 10 = 89 元
严重度：S2（金额错误，涉及资损）
优先级：P0（影响所有用券用户）
复现率：必现（5/5）
附件：结算页截图、订单快照、traceId=abc123
```

## 六、缺陷生命周期

`新建(New) → 已确认(Confirmed) → 修复中(In Progress) → 待验证(Fixed) → 已关闭(Closed)`
旁路：`拒绝(Rejected/不是问题) / 重复(Duplicate) / 延期(Deferred) / 无法复现(Cannot Reproduce)`。

- 关闭必须由**报告者或测试验证**，开发不自行关闭。
- "无法复现"需补充环境/日志再回归，不直接关闭。
- "延期/拒绝"需说明理由并由产品确认。

## 七、质量度量（供发布决策）

- 缺陷密度、按严重度分布、修复时长、重开率（reopen rate）、遗留缺陷数与风险。
- 关注**趋势**而非单点：临近发布仍有 S1/S2 未收敛，应推迟发布。
