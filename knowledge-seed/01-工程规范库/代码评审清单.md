# 代码评审清单（Code Review Checklist）

> 用途：作为代码评审员（Reviewer）逐项核对的标准。评审的目标不是"挑错"，而是**在合入前把缺陷、风险、可维护性问题拦截在最便宜的阶段**。
> 使用建议：把本清单挂载给「代码评审员」Agent，评审时要求它按"正确性 → 安全 → 可维护性 → 测试 → 性能"的优先级逐项检查并按严重度排序输出。

## 一、评审前的准入（作者自检，Reviewer 有权打回）

- [ ] PR 描述说明了**改了什么、为什么改、如何验证**，并关联需求/缺陷单。
- [ ] 变更范围聚焦单一目的，diff 行数可控（建议 < 400 行；超出应拆分）。
- [ ] 本地已通过编译、Lint、单元测试；CI 为绿。
- [ ] 无未说明的无关改动（格式化、重命名与业务改动混在一起会淹没评审重点）。
- [ ] 敏感信息（密钥、token、内网地址、真实用户数据）未进入代码或日志。

## 二、正确性（最高优先级）

- [ ] 实现是否满足需求/验收标准？边界条件（空、0、负数、超大、并发）是否处理？
- [ ] 错误路径是否被处理？异常是被吞掉还是被正确传播/记录？
- [ ] 空指针/未定义：可选值在使用前是否校验？
- [ ] 并发与竞态：共享状态是否有保护？是否存在 check-then-act 竞态？
- [ ] 幂等性：重试、重复提交、消息重复消费是否会造成副作用？
- [ ] 事务边界是否正确？失败是否回滚？跨服务操作是否考虑最终一致性？

## 三、安全

- [ ] 所有外部输入（请求参数、Header、文件、上游返回）是否校验与转义？
- [ ] SQL/命令/模板注入：是否使用参数化查询、避免字符串拼接执行？
- [ ] 鉴权与越权：是否校验"当前用户是否有权操作该资源"（而不仅是"是否登录"）？
- [ ] 敏感数据是否最小化返回？日志是否脱敏（不打印密码、token、身份证等）？
- [ ] 依赖是否引入已知漏洞版本？新依赖是否必要、来源可信？

## 四、可维护性与可读性

- [ ] 命名是否表意清晰？函数是否单一职责、长度可控？
- [ ] 是否有"魔法数字/字符串"应提为常量？重复逻辑是否应抽取？
- [ ] 注释是否解释"为什么"而非复述"做了什么"？过时注释是否清理？
- [ ] 是否与现有代码风格、分层约定一致（不自创模式）？
- [ ] 复杂逻辑是否有足够的可读性（早返回、拆分、去嵌套）？

## 五、测试

- [ ] 新增/变更逻辑是否有对应测试？覆盖正常路径 + 关键异常/边界。
- [ ] 测试是否可独立运行、无隐藏依赖、无随机不稳定（flaky）？
- [ ] 测试断言的是"行为/契约"而非"实现细节"？
- [ ] 修复缺陷时，是否补了能复现该缺陷的回归测试？

## 六、性能与资源

- [ ] 是否存在 N+1 查询、循环内 IO、不必要的全表扫描？
- [ ] 大集合是否分页/流式处理？是否有内存无界增长风险？
- [ ] 是否新增了热路径上的同步阻塞调用？
- [ ] 缓存是否有失效策略？是否可能缓存脏数据？

## 七、评审沟通规范

- **区分等级**：用前缀标注意见，降低沟通成本。
  - `[blocker]` 必须修复才能合入（正确性/安全）。
  - `[should]` 强烈建议修复（可维护性/测试缺口）。
  - `[nit]` 吹毛求疵，作者可自行取舍。
  - `[question]` 我没看懂，请解释（不预设对错）。
- 对事不对人；给出**建议方案**而非仅指出问题；引用规范/事实而非个人偏好。
- 作者：逐条回应，不默默改；有分歧先讨论再动手。

## 八、合入前最终确认

- [ ] 所有 `[blocker]` 已解决，`[should]` 已解决或达成一致。
- [ ] CI 全绿，冲突已解决。
- [ ] 变更是否需要同步：文档、配置、迁移脚本、灰度/回滚方案、监控告警。
