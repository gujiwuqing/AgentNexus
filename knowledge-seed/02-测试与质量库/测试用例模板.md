# 测试用例模板与编写规范

> 用途：统一测试用例的字段与写法，保证可执行、可复现、可度量。
> 使用建议：挂载给「测试设计师」Agent，要求它按本模板输出用例集。

## 一、用例字段定义

| 字段 | 说明 | 是否必填 |
| --- | --- | --- |
| 用例ID | 唯一编号，如 `TC-ORDER-001` | 是 |
| 标题 | 一句话说明验证点 | 是 |
| 所属模块/需求 | 关联需求或功能点 | 是 |
| 优先级 | P0/P1/P2（见下） | 是 |
| 用例类型 | 功能/边界/异常/性能/安全/兼容 | 是 |
| 前置条件 | 执行前必须满足的状态/数据 | 是 |
| 测试数据 | 具体输入数据 | 是 |
| 操作步骤 | 有序、可执行、无歧义 | 是 |
| 预期结果 | 可验证的具体结果（含状态/数据/提示） | 是 |
| 实际结果 | 执行时填写 | 执行时 |
| 结果 | Pass/Fail/Blocked | 执行时 |
| 备注 | 依赖、已知问题等 | 否 |

## 二、优先级定义

- **P0（冒烟/核心）**：核心业务主流程，失败即阻断发布。每次回归必跑。
- **P1（重要）**：重要功能与常见异常路径，失败影响主要体验。
- **P2（一般）**：次要功能、边缘场景、提示文案等。

## 三、编写规范

1. **一个用例只验证一个点**，标题即验证点；不要把多个校验塞进一条。
2. **步骤可执行、无歧义**：任何人照着做都能得到相同结果；写清具体数据而非"输入一些数据"。
3. **预期结果可验证**：写"提示『手机号格式不正确』且不创建记录"，而不是"提示错误"。
4. **前置条件写全**：账号、权限、数据状态、环境开关。
5. **正反都要覆盖**：既测"应该成功"，也测"应该失败/被拒"。
6. **独立可重复**：用例之间无隐藏依赖，可单独执行、可重复执行。

## 四、用例示例（登录）

```
用例ID：TC-AUTH-003
标题：密码错误时登录失败并提示，且不返回用户信息
所属：用户认证 / 需求 REQ-AUTH-01
优先级：P0
类型：异常
前置条件：存在账号 test@example.com，密码为 Correct#123
测试数据：邮箱 test@example.com，密码 Wrong#000
步骤：
  1. 打开登录页
  2. 输入邮箱 test@example.com
  3. 输入密码 Wrong#000
  4. 点击"登录"
预期结果：
  1. 返回 401，错误码 invalid_credentials
  2. 页面提示"邮箱或密码不正确"
  3. 未下发会话 Cookie，未跳转
  4. 不在响应中泄漏"该邮箱是否存在"（防用户枚举）
```

## 五、边界值用例示例（分页参数）

| 用例ID | 输入 pageSize | 预期 |
| --- | --- | --- |
| TC-PAGE-001 | 1 | 成功，返回 1 条 |
| TC-PAGE-002 | 100（上限） | 成功，最多返回 100 条 |
| TC-PAGE-003 | 0 | 400 参数校验失败 |
| TC-PAGE-004 | 101（超上限） | 400 或被夹到 100（按契约）|
| TC-PAGE-005 | "abc" | 400 参数校验失败 |

## 六、评审用例的检查点

- [ ] 是否覆盖了需求的每条验收标准？
- [ ] 是否覆盖了边界、异常、权限、并发？
- [ ] 预期结果是否具体可验证？
- [ ] 是否存在重复/冗余用例可合并？
- [ ] 优先级分配是否合理（别把所有都标 P0）？
