# 架构决策记录（ADR）模板与示例

> 用途：把"为什么这样设计"沉淀下来。架构决策记录（Architecture Decision Record）让后来者理解决策背景与取舍，避免重复踩坑或盲目推翻。
> 使用建议：挂载给「技术方案师」「深度研究员」Agent，要求它把技术方案以 ADR 形式沉淀，并在评审时检查关键决策是否有 ADR。

## 一、ADR 是什么、为什么

- 一条 ADR 记录**一个**有影响力的技术决策：背景、可选方案、最终选择、后果。
- 目的不是文档留档，而是**保留决策的上下文**——半年后没人记得"当时为什么不用 X"。
- 特点：轻量（一页内）、不可变（决策变了写新的 ADR 取代旧的，而非改旧的）、按编号归档。

## 二、什么决策值得写 ADR

- 影响面广、难以逆转、成本高的决策：
  - 技术栈/框架/数据库选型
  - 服务拆分与边界、通信方式（同步/异步）
  - 数据一致性策略、缓存策略
  - 鉴权与安全方案
  - 关键第三方依赖的引入
- 判断标准：**如果做错了，纠正成本很高** → 写 ADR。

## 三、ADR 模板

```
# ADR-<编号>：<决策标题>

- 状态：提议 / 已接受 / 已废弃 / 被 ADR-XXX 取代
- 日期：YYYY-MM-DD
- 决策者：<人/小组>

## 背景（Context）
我们面临什么问题？有哪些约束（业务、技术、时间、团队能力、合规）？
决策的驱动因素是什么？

## 可选方案（Options）
- 方案 A：描述 / 优点 / 缺点 / 成本
- 方案 B：描述 / 优点 / 缺点 / 成本
- 方案 C：……

## 决策（Decision）
我们选择 <方案X>，因为 <关键理由>。

## 后果（Consequences）
- 正面：我们得到了什么。
- 负面/代价：引入了什么复杂度、限制、技术债。
- 后续：需要配套做什么（迁移、监控、文档、团队培训）。

## 备注
相关 ADR、参考资料、待验证的假设。
```

## 四、示例 ADR

```
# ADR-007：工作流执行采用 MySQL 队列 + 进程内 Worker，暂不引入 Redis/MQ

- 状态：已接受
- 日期：2026-07-24
- 决策者：后端小组

## 背景
工作流可能运行数分钟（多次 LLM 调用），不能在 HTTP 请求内同步执行，
否则会阻塞请求、超时、无法水平扩展。需要一种异步执行与任务领取机制。
约束：团队规模小，运维能力有限，希望减少新增基础设施。

## 可选方案
- A. 引入 Redis + BullMQ：成熟、功能全；但新增一套需运维的基础设施与故障域。
- B. 引入消息队列（RabbitMQ/Kafka）：能力强；对当前规模过重，学习与运维成本高。
- C. 用 MySQL 做载体队列 + 进程内 Worker 轮询领取（乐观锁 + 租约）：
     复用现有数据库，无新增组件；吞吐上限较低，但满足当前量级。

## 决策
选择 C。当前量级下 MySQL 队列足够，避免过早引入 Redis/MQ 的运维负担。
领取用乐观锁（条件 UPDATE + affectedRows），崩溃用租约过期感知。

## 后果
- 正面：零新增基础设施；事务与数据在同一个库，简单可靠。
- 代价：吞吐受 DB 限制；需要自己实现租约、重试、僵尸回收逻辑。
- 后续：埋点监控队列积压与执行时长；量级增长到阈值时重新评估引入专用 MQ（届时写新 ADR 取代本条）。
```

## 五、实践建议

- ADR 存放在仓库内（如 `docs/adr/`），随代码一起版本化、评审。
- 编号递增、不复用；废弃的 ADR 保留并标注被谁取代。
- 在 PR/方案评审中链接相关 ADR，让评审者看到决策依据。
- ADR 不是越多越好——只记"值得记住的决策"，避免变成流水账。
