# API 设计准则（RESTful / HTTP API）

> 用途：统一后端对外接口的设计风格，覆盖资源建模、状态码、错误结构、分页、版本、幂等与安全。
> 使用建议：挂载给「技术方案师」「代码评审员」Agent，用于设计接口方案或评审接口是否规范。

## 一、资源与 URL

- 用**名词复数**表示资源集合：`/users`、`/orders`、`/orders/{id}/items`。
- 用 HTTP 动词表达操作，**不要把动词放进 URL**：
  - ✅ `POST /orders` ❌ `POST /createOrder`
- 层级表达从属关系：`/users/{userId}/orders`。
- 过滤、排序、分页用查询参数：`/orders?status=paid&sort=-createdAt&page=2&pageSize=20`。
- 对确实非 CRUD 的动作，可用子资源或动作端点并说明：`POST /orders/{id}:cancel` 或 `POST /orders/{id}/cancellation`。

## 二、HTTP 方法语义

| 方法 | 语义 | 幂等 | 典型状态码 |
| --- | --- | --- | --- |
| GET | 读取，无副作用 | 是 | 200 |
| POST | 创建 / 触发动作 | 否 | 201（创建）/ 200 |
| PUT | 全量替换 | 是 | 200 / 204 |
| PATCH | 部分更新 | 否（视实现） | 200 |
| DELETE | 删除 | 是 | 204 / 200 |

## 三、状态码

- `200 OK` 成功；`201 Created` 创建成功（返回资源或 `Location`）；`204 No Content` 成功无返回体。
- `400` 参数校验失败；`401` 未认证；`403` 已认证但无权限；`404` 资源不存在。
- `409` 冲突（如唯一约束、状态不允许）；`422` 语义校验失败（可选）；`429` 触发限流。
- `500` 服务端异常；`503` 依赖不可用。
- **原则**：客户端能纠正的错误用 4xx，服务端问题用 5xx；不要一律返回 200 再在 body 里塞 error。

## 四、统一响应与错误结构

成功直接返回资源数据。错误使用**统一结构**，便于客户端统一处理：

```json
{
  "error": {
    "code": "order_not_found",
    "message": "The order does not exist or has been deleted",
    "details": [
      { "field": "orderId", "issue": "not_found" }
    ]
  }
}
```

- `code`：**机器可读**的稳定错误码（不随文案变化），客户端据此分支处理。
- `message`：人类可读说明，可用于日志/提示（面向终端用户需二次本地化）。
- `details`：可选，字段级校验错误等结构化细节。

## 五、分页

- 统一约定一种风格并全站一致：
  - **偏移分页**：`?page=&pageSize=`，响应含 `total`、`page`、`pageSize`。适合可跳页。
  - **游标分页**：`?cursor=&limit=`，响应含 `nextCursor`。适合大数据量/实时流，避免深翻页性能问题。
- `pageSize` 设默认值与上限（如默认 20、上限 100），防止一次拉取过大。

## 六、版本管理

- 对外 API 引入版本，优先 **URL 版本**：`/v1/orders`（直观、易缓存、易路由）。
- 破坏性变更升 `v2`，旧版本保留并公告弃用（Deprecation）时间表。
- 非破坏性变更（新增字段、新增可选参数）不升版本；客户端应容忍未知字段。

## 七、幂等性

- `GET/PUT/DELETE` 天然幂等；`POST` 创建类接口通过 **Idempotency-Key** 头保证幂等：
  - 客户端生成唯一 key 随请求携带；服务端对同一 key 返回首次结果，避免重复下单/重复扣款。
- 支付、下单、退款等**涉及资金/资源**的写接口必须设计幂等。

## 八、请求与数据约定

- 请求/响应体统一 `application/json`，字段命名风格全站一致（`camelCase` 或 `snake_case` 二选一）。
- 时间统一用 ISO 8601 + 时区（`2026-07-30T10:00:00Z`），金额用最小单位整数或字符串定点数，避免浮点误差。
- 枚举值用稳定字符串常量，不用魔法数字。
- 布尔字段语义明确，避免三态歧义（用可空或独立字段表达"未知"）。

## 九、安全

- 全站 HTTPS；鉴权用 `Authorization: Bearer <token>`。
- **鉴权 ≠ 授权**：每个接口都校验"当前身份能否操作该资源"，防越权（IDOR）。
- 输入全部校验；输出最小化（不泄漏内部字段、堆栈、SQL）。
- 写接口做限流与防重放；敏感操作二次确认/审计日志。
- CORS、CSRF 按场景配置；错误信息不暴露实现细节。

## 十、可观测性与契约

- 关键接口埋点：QPS、时延分位（P50/P95/P99）、错误率。
- 用 OpenAPI/Swagger 维护契约，作为前后端与测试的单一事实来源。
- 契约变更走评审；对外接口变更需通知消费方并提供迁移期。

## 十一、评审检查要点

- [ ] URL 是名词、方法语义正确、状态码恰当。
- [ ] 错误结构统一、错误码稳定可分支。
- [ ] 分页/排序/过滤风格一致且有上限。
- [ ] 写接口的幂等与并发冲突已考虑。
- [ ] 鉴权、越权、输入校验、输出脱敏到位。
- [ ] 契约文档同步更新。
