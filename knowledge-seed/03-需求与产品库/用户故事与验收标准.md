# 用户故事与验收标准

> 用途：把需求写成研发可实现、测试可验证的用户故事 + 验收标准（Acceptance Criteria）。
> 使用建议：挂载给「需求分析师」Agent，要求它把粗略诉求拆成 INVEST 用户故事并配 Given-When-Then 验收标准。

## 一、用户故事格式

```
作为 <角色>，
我想要 <目标/能力>，
以便 <价值/收益>。
```

**示例**：
> 作为已注册用户，我想要用邮箱重置密码，以便在忘记密码时仍能登录，而不必联系客服。

要点：
- 站在**用户价值**角度，而非功能实现角度。
- 一个故事对应一个可独立交付的价值切片。
- "以便"部分说明为什么做，帮助排优先级和取舍。

## 二、INVEST 原则（好故事的标准）

| 字母 | 含义 | 说明 |
| --- | --- | --- |
| I | Independent 独立 | 尽量可独立开发与交付，减少强依赖 |
| N | Negotiable 可协商 | 是需求而非契约，细节可讨论 |
| V | Valuable 有价值 | 对用户/业务有明确价值 |
| E | Estimable 可估算 | 能估工作量，太大或太模糊要拆 |
| S | Small 小 | 能在一个迭代内完成 |
| T | Testable 可测试 | 有明确验收标准 |

## 三、验收标准（Given-When-Then）

每个故事配一组验收标准，覆盖正常流 + 异常流：

```
场景：<场景名>
Given <前置条件/初始状态>
When  <用户执行的操作>
Then  <可观察、可验证的预期结果>
```

**示例（邮箱重置密码）**：
```
场景1：成功发送重置邮件
Given 存在邮箱为 user@example.com 的账号
When  用户在"忘记密码"页提交该邮箱
Then  系统发送含有效期 30 分钟的重置链接的邮件
And   页面提示"重置邮件已发送，请查收"

场景2：邮箱未注册（防用户枚举）
Given 系统不存在邮箱 ghost@example.com
When  用户提交该邮箱
Then  页面仍提示"若该邮箱已注册，将收到重置邮件"（不泄漏是否存在）
And   不发送任何邮件

场景3：重置链接过期
Given 用户持有一个 31 分钟前生成的重置链接
When  用户打开该链接并提交新密码
Then  提示"链接已失效，请重新申请"
And   密码未被修改
```

## 四、验收标准的质量要求

- **可验证**：结果是客观可观察的（状态、数据、提示、跳转），不用"体验好""合理"这类词。
- **覆盖异常**：空、错误输入、越权、并发、超时、幂等等。
- **明确边界**：数值范围、时效、数量上限。
- **不含实现细节**：描述"做什么"（行为/契约），不规定"怎么实现"（除非是硬约束）。

## 五、拆分大故事（Story Splitting）常用维度

当故事太大无法在一个迭代完成时，按以下维度拆：
- 按**操作步骤**（增/删/改/查分开）。
- 按**业务规则/场景**（先主流程，再各分支）。
- 按**数据类型/输入**（先支持一种，再扩展）。
- 按**接口/端**（先后端能力，再前端；先 Web，再移动端）。
- 按**性能/规模**（先跑通，再优化到目标性能）。
- **纵向切片优先**：每个切片都端到端可用、可交付价值，而不是横向按层拆。

## 六、就绪定义（Definition of Ready）—— 进开发前

- [ ] 有清晰的用户故事与价值说明。
- [ ] 有可验证的验收标准（含异常）。
- [ ] 依赖已识别、无阻塞。
- [ ] 设计稿/接口契约就绪（如需要）。
- [ ] 团队已估算且大小合适（可在一个迭代完成）。

## 七、完成定义（Definition of Done）—— 认为完成

- [ ] 代码完成并通过评审、合入主干。
- [ ] 验收标准全部通过（开发自测 + 测试验证）。
- [ ] 自动化测试补齐，CI 绿。
- [ ] 文档/埋点/配置同步。
- [ ] 产品验收通过。
