# 发布准入清单（Release Readiness Checklist）

> 用途：在把变更推向生产前，逐项确认"是否真的可以发布"。目标是把发布从"赌一把"变成"走流程"。
> 使用建议：挂载给「测试设计师」「技术方案师」Agent，用于生成发布检查单、评估发布风险、制定回滚预案。

## 一、功能与质量

- [ ] 需求验收标准全部满足，产品已验收。
- [ ] P0/P1 测试用例全部通过；冒烟用例通过。
- [ ] 无未关闭的 S1/S2 缺陷；遗留缺陷有记录、有风险评估、产品已知悉接受。
- [ ] 回归测试通过（受影响模块 + 核心链路）。

## 二、兼容性与数据

- [ ] 数据库变更：迁移脚本经过评审，**向后兼容**（先兼容再清理，避免与旧代码冲突）。
- [ ] 迁移可回滚或有数据修复方案；大表变更评估锁表/耗时影响。
- [ ] 接口变更向后兼容；若破坏性变更，消费方已通知并完成适配或走版本。
- [ ] 灰度期间新旧代码/新旧数据并存无冲突。

## 三、配置与依赖

- [ ] 新增配置项已在各环境（预发/生产）就位，且有默认值兜底。
- [ ] 特性开关（Feature Flag）就绪，可快速关闭新功能。
- [ ] 第三方依赖/下游服务的容量、限流、超时、降级已确认。
- [ ] 密钥/证书在安全配置中，未硬编码。

## 四、性能与容量

- [ ] 核心接口压测通过，满足时延（P95/P99）与吞吐目标。
- [ ] 评估新增负载对 DB/缓存/下游的冲击；必要时提前扩容。
- [ ] 无慢查询、无 N+1、无明显内存增长风险。

## 五、安全与合规

- [ ] 鉴权/越权校验到位；敏感数据脱敏；日志不含隐私。
- [ ] 依赖无已知高危漏洞；新增外部调用可信。
- [ ] 涉及个人信息/资金的变更符合合规要求，必要时法务/安全评审。

## 六、可观测性

- [ ] 关键路径有日志、埋点、traceId，便于事后排查。
- [ ] 新增/变更功能配套监控指标与告警阈值。
- [ ] 有可用的 Dashboard 观察发布后核心指标（成功率、时延、错误率、业务量）。

## 七、发布与回滚预案

- [ ] 发布方式确定：灰度/分批/全量，及各阶段观察时长与放量比例。
- [ ] **回滚方案明确且演练过**：如何回滚代码、配置、数据；回滚耗时可接受。
- [ ] 回滚触发条件量化（如错误率 > X%、核心指标下跌 > Y%）。
- [ ] 发布窗口避开业务高峰；关键人员在场（研发/测试/运维/产品）。
- [ ] 发布 checklist、负责人、联系方式、应急预案已同步到相关方。

## 八、发布后验证（Post-Deploy）

- [ ] 冒烟核心链路（真实环境验证下单/支付/登录等关键路径）。
- [ ] 观察监控 15~60 分钟：错误率、时延、业务量无异常。
- [ ] 灰度指标达标后再扩大放量。
- [ ] 记录发布结论（成功/回滚/观察中）与遗留事项。

## 九、发布决策原则

- 临近窗口仍有未收敛的 S1/S2、无回滚方案、监控缺失 → **不发布**。
- "能发"和"该发"是两回事：高风险变更避免在周五/节假日前发布。
- 一次只改一个大变量；多个高风险变更不要挤在同一次发布。
